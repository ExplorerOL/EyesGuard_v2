# skill-create-ai-ready-task

Создай файл `ai-ready-task.md` — задачу для ИИ-агента, впервые видящего проект.
Навык производит файл-артефакт, не решает предметную задачу.

## Триггеры

- «оформи задачу по ai-ready шаблону»
- «подготовь ТЗ для агента» / «сделай задачу для ИИ»
- «опиши задачу так, чтобы агент сделал без вопросов»
- пользователь называет блок шаблона: Problem, Expected outcome, Non-goals и т.п.

## Правила взаимодействия

1. **Не превращай в анкету.** Задавай 1–3 вопроса за раз, не все сразу.
2. **Ищи в коде, не спрашивай.** Если факт извлекается из проекта (codegraph, файлы, README, AGENTS.md, база знаний .agents) — найди сам, покажи пользователю, спроси подтверждение.
3. **Не блокируй.** Поле, которое по правилам можно опустить, — опусти, не требуй ответа.
4. **Фиксируй дословно.** Бизнес-правила, формулировки ошибок, ограничения записывай словами пользователя.
5. **Не выдумывай.** Пути, имена методов, команды — только из проекта. Чего нет — скажи, что не нашёл.

## Шаги

### 0. Получи контекст

Прочитай файл или директорию, если передан путь. При вызове из
`skill-implement-task` также прочитай `task.md` и существующие `research.md`,
`decisions.md` и `status.md`; не запрашивай у пользователя уже записанные факты.

### 1. Уточни рамки

Спроси 1–3 вопроса:
- Тип задачи: фича / баг / рефакторинг / исследование?
- Какой код/модуль/артефакт затрагивается?
- Есть ли бизнес-контекст, который агент не получит из кода?

### 2. Собери поля шаблона

Собирай в порядке:
1. Problem → 2. Expected outcome → 3. Known facts → 4. Hypotheses →
5. Constraints → 6. Non-goals → 7. Source of truth → 8. Required checks →
9. Stop conditions

Для каждого поля выявляй неопределённость вопросами из секции «Поля». Пропускай
поля, которые можно опустить (см. «Когда опустить»).

### 3. Дозаполни из кода

Для Known facts, Constraints, Source of truth, Required checks — используй:
- codegraph — структура, вызовы, зависимости, символы
- чтение файлов — README, AGENTS.md, миграции, конфиги
- grep/glob — поиск паттернов, путей, имён

Подставляй точные пути, реальные имена методов, команды сборки и тестов проекта.

### 4. Создай файл

При самостоятельном запуске по умолчанию создай `ai-ready-task.md` в корне
проекта; при необходимости уточни расположение. При вызове из
`skill-implement-task` используй строго переданный output-path —
`.agents/tasks/<task-name>/ai-ready-task.md`, не корень проекта.

Включай только применимые поля. Опущенное поле не пиши или пометь
`<!-- не применимо -->`. В Source of truth добавь относительные ссылки на
существующие `research.md`, `decisions.md` и другие материалы задачи, если они есть.

### 5. Проверь результат

Пройдись по чек-листу:
- [ ] Problem — конкретное действие с целевым артефактом, не общая цель
- [ ] Expected outcome — проверяемый критерий «достаточно»
- [ ] Known facts — все решения, которые агент не должен переоткрывать
- [ ] Constraints — чего нельзя делать
- [ ] Non-goals — что вне объёма
- [ ] Source of truth — конкретные файлы/документы
- [ ] Required checks — конкретные команды
- [ ] Stop conditions — критерий остановки

## Шаблон

```markdown
# AI-ready task

## Problem

## Expected outcome

## Known facts

## Hypotheses

## Constraints

## Non-goals

## Source of truth

## Required checks

## Stop conditions
```

## Поля

### Problem
Опиши конкретное действие с целевым артефактом. Укажи файл/функцию/API, который
меняется. Если важно — начальное состояние. Без общих фраз и «почему».

Спроси: «Каким одним глаголом описать результат?», «Какой файл/эндпоинт меняется?»,
«Что сейчас неверно — с примером?»

### Expected outcome
Опиши проверяемый артефакт результата. Укажи формат (файл, ответ API, колонка БД),
критерий проверяемости, количество изменений, эффект на систему.

Спроси: «Что появится после выполнения?», «Как проверим результат?», «Какого
минимума хватит для "готово"?»

### Known facts
Запиши принятые решения, что пробовали и почему не сработало, существующие
ограничения, ссылки на предыдущие задачи, бизнес-правила и термины, которых нет
в коде.

Спроси: «Что уже решено?», «Что пробовали и почему не сработало?», «Какие
бизнес-правила агент не узнает из кода?»

### Hypotheses
Запиши предположения о причине проблемы, ожидаемый эффект решения, способ
проверки, альтернативные гипотезы.

Спроси: «Какая вероятная причина?», «Как проверим?», «Какие ещё могут быть причины?»

### Constraints
Зафиксируй технологические запреты, модульные границы, версионные ограничения,
code style, ограничения безопасности и производительности.

Спроси: «Чего НЕльзя делать?», «Какие модули не трогать?», «Какие правила проекта
обязательны?»

### Non-goals
Перечисли смежные задачи и улучшения, которые осознанно откладываешь. Укажи
системные границы — что не меняется.

Спроси: «Что НЕ входит в задачу, даже если логично?», «Какие улучшения откладываем?»

### Source of truth
Укажи ссылки на документацию (Confluence, README, ADR), пути к эталонному коду,
API-спецификации, схемы БД, тестовые данные, прошлые тикеты.

Спроси: «Где агент найдёт правильный ответ?», «Какой код — эталон?», «На какие
тикеты сослаться?»

### Required checks
Укажи конкретные команды тестов и линтеров, метрики покрытия, ручные и
интеграционные проверки, что нельзя сломать.

Машинно-проверяемые критерии (сверка эталонов, запрет-импорты, лимиты) оформляй
как контракт будущего `scripts/verify.py` в директории задачи: что скрипт
проверяет и что считается успехом. Ревью задачи прогоняет verify.py первым.

Спроси: «Какие тесты/линтеры прогнать?», «Что проверить вручную?», «Что нельзя
допустить перед сдачей?»

### Stop conditions
Укажи порог качества, число итераций, критерий «достаточно хорошо», сигнал
завершения, что делать с остаточными проблемами.

Спроси: «Когда остановиться?», «Что сигналит "готово"?», «Куда деть мелкие
замечания?»

## Когда опустить поле

- **Problem** — действие из одной команды («смержить ПР #42») или декоративная правка.
- **Expected outcome** — результат тривиален или очевиден из Problem.
- **Known facts** — контекст исчерпывается Problem, задача изолирована.
- **Hypotheses** — нет неопределённости, причина очевидна.
- **Constraints** — полностью заменяется Non-goals, окружение строго изолировано.
- **Non-goals** — scope не расширить из формулировки Problem.
- **Source of truth** — все детали в Problem, используется стандартная библиотека.
- **Required checks** — задача не создаёт код или всё покрыто CI.
- **Stop conditions** — дублирует Expected outcome или результат нельзя перешлифовать.

## Шпаргалка

| Поле | Защищает от |
|---|---|
| Problem | Агент делает не то |
| Expected outcome | Готово без результата / бесконечные улучшения |
| Known facts | Перепроектирует решённое |
| Hypotheses | Чинит следствие, не причину |
| Constraints | Ломает соседние модули |
| Non-goals | Делает «заодно» |
| Source of truth | Выдумывает API и факты |
| Required checks | Сдаёт неработающий код |
| Stop conditions | Шлифует бесконечно |

## Пример

```markdown
# AI-ready task

## Problem
Добавить gRPC-эндпоинт CreateRefund в CompensationsGrpcServiceV2, который по
claimId создаёт запись рефанда. Сейчас рефанд создаётся только внутри use-case
ApproveRefund, отдельного эндпоинта нет.

## Expected outcome
Новый метод CreateRefund в сервисе v2; вызов POST /refund → возвращает
RefundCreated с id рефанда. Если claimId не существует — ошибка CLAIM_NOT_FOUND.

## Constraints
- Не изменять контракты существующих методов v2.
- Не добавлять БД-миграции и внешние зависимости.
- Следовать паттерну use-case'ов в
  src/Ozon.CML.C2CCompensations.Application.UseCases/ApproveRefund/.

## Non-goals
- Не рефакторить ApproveRefund и остальные методы сервиса.
- Не добавлять swagger-спецификацию.

## Source of truth
- Эталон: src/Ozon.CML.C2CCompensations.Application.UseCases/ApproveRefund/
  (ApproveRefundCommand, валидатор, хендлер).
- Контракт сервиса v2: proto в каталоге Presentation.Grpc.
- README → секция «Grpc-сервисы».

## Required checks
- `dotnet build Ozon.CML.C2CCompensations.sln` — 0 предупреждений.
- `dotnet test` — все тесты зелёные.

## Stop conditions
- Эндпоинт создан, сборка чистая, тесты зелёные. Мелкие улучшения не делаем.
```
